# GlobalLogic Internal Documentation

## Company Overview

GlobalLogic is a digital engineering company that helps organizations design and build digital products and experiences. The company works with clients across different industries and provides engineering, software development, cloud, data, and digital product services.

GlobalLogic teams commonly work on software applications, cloud platforms, data engineering systems, artificial intelligence solutions, and digital transformation projects. Engineering teams collaborate across different locations and use modern development practices to build and maintain software systems.

## DocMind Project

DocMind is an internal documentation assistant designed to help employees search and understand internal technical documentation. The system allows users to upload documents and prepares those documents for semantic search and question answering.

The main purpose of DocMind is to reduce the time required to find information inside large collections of internal documents. Instead of manually searching through many files, a user can ask a question and the system can identify relevant parts of the available documentation.

The project is divided into multiple stages. The first stage handles document upload and storage. The second stage prepares documents for semantic retrieval by creating chunks and embeddings. A later stage can use those embeddings to retrieve relevant information and provide grounded answers.

## Document Upload

When a user uploads a document, the API receives the file and validates it before storing it. The actual file is stored in local storage, while document metadata is maintained separately.

The metadata can include the document identifier, original filename, upload time, file path, and processing status. Keeping metadata separate from the physical file makes it easier to manage documents and track their processing state.

Supported text-based documents can be processed by extracting their text content. After extraction, the text becomes the input for the chunking stage.

## Document Chunking

Large documents should not normally be sent to an embedding model as one large piece of text. Instead, the document is divided into smaller sections called chunks.

DocMind uses a fixed-size chunking approach. The current configuration uses approximately 500 tokens per chunk with an overlap of approximately 50 tokens between consecutive chunks.

For example, if the first chunk contains information near the end of a section, some of that information is repeated at the beginning of the next chunk. This overlap helps reduce the possibility of losing context when an important sentence or explanation is located near a chunk boundary.

Each generated chunk receives a unique identifier and a sequence number. The sequence number represents the position of the chunk within the original document.

The chunk also keeps the document identifier and source information such as the filename. This metadata can later help identify where retrieved information came from.

## Chunking Example

Consider a technical document containing information about application architecture, APIs, databases, authentication, logging, testing, and deployment.

If the complete document is too large for a single chunk, the chunking service divides it into multiple pieces.

Chunk 1 contains the beginning of the document. Chunk 2 contains the next section while also keeping a small portion of the previous content because of the configured overlap. Chunk 3 continues the same process until the complete document has been processed.

This creates smaller units that can be independently converted into embeddings and searched later.

## Embeddings

After chunking, each chunk is converted into a numerical representation called an embedding.

DocMind uses the local nomic-embed-text model through Ollama for this step. The embedding represents the semantic meaning of the chunk as a vector of numbers.

Two chunks discussing similar concepts can have similar vector representations even when they use different words. This property allows semantic search to find relevant information based on meaning rather than only exact keyword matches.

The embedding process is performed for each chunk generated by the chunking service.

## Vector Database

DocMind uses Qdrant as the vector database.

The generated embedding vectors are stored in Qdrant together with useful metadata. The payload can contain the document ID, chunk ID, sequence number, chunk text, filename, and section information when available.

The vector collection uses a vector size of 768 and cosine similarity for comparing vectors.

Qdrant is used because the vectors need to be searched efficiently when a user asks a question in the later retrieval stage.

## Ingestion Pipeline

The complete Phase 2 ingestion process can be represented as:

Document upload → file storage → text extraction → chunking → embedding generation → Qdrant storage.

The ingestion process is handled in the background. A document ID is placed into an in-memory channel after upload. A background worker reads the document ID and starts the processing pipeline.

The document status can move from Uploaded to Processing and finally to Indexed when the vectors have been successfully stored.

If processing fails, the system can record a failure status and the reason for the failure.

## Reprocessing

A document may need to be processed again if its content changes or if ingestion needs to be repeated.

Before inserting new vectors for a document, the existing vectors associated with that document are removed from Qdrant. The document is then chunked and embedded again.

This prevents old vectors from remaining alongside the new vectors and reduces the possibility of retrieving outdated information.

## Document Deletion

When a document is deleted, its associated vectors should also be removed from Qdrant.

This keeps the vector database consistent with the document store. The physical document, document metadata, and vector representations should not remain after the document has been deleted.

## Retrieval Preparation

The output of Phase 2 is a searchable collection of document chunks and their embeddings.

For example, a document may produce many chunks. Each chunk has its own vector and metadata. These vectors can later be compared with the vector representation of a user's question.

The most relevant chunks can then be selected and provided as context to a language model.

## Future Question Answering

In the retrieval and chat stage, a user can submit a question about the internal documentation.

The question can first be converted into an embedding using the same embedding model. The system can then search Qdrant for chunks with similar vector representations.

The retrieved chunks provide the relevant context for generating an answer. The final response can include citations or source information so that the user can understand which document content was used.

The overall future flow is:

User question → question embedding → Qdrant similarity search → relevant document chunks → local language model → grounded answer.

## Testing

The project also includes automated tests for important parts of the ingestion pipeline.

Chunking tests can verify empty input, short documents, chunk boundaries, overlap, and configurable chunk sizes.

Ingestion tests can use mocked embedding and vector-store dependencies. This allows the business logic to be tested without requiring a real Ollama model or Qdrant instance for every test.

Integration testing can additionally verify the behavior against local infrastructure when required.

## Summary

DocMind Phase 2 prepares internal documents for semantic search. The system extracts document text, divides it into overlapping chunks, generates local embeddings, and stores the vectors and metadata in Qdrant.

The main goal is to create a reliable searchable representation of the documentation that can be used by the retrieval and question-answering functionality in the next stage.
